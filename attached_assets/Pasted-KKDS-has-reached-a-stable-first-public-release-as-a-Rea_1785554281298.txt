KKDS has reached a stable first public release as a React web design system.

I want to evolve the architecture so it can eventually support both:

- React + Next.js (web)
- React Native + Expo (mobile)

without compromising the quality of either platform.

This is NOT a request to build a React Native implementation today.

Instead, I want you to perform an architectural review and refactor KKDS so it is ready for future cross-platform expansion.

Think like a Staff Design Systems engineer designing the architecture for the next several years.

---

GOALS

The design system should eventually consist of three logical layers:

1. kkds-common

Contains platform-neutral concepts.

Examples:

- design tokens
- semantic color roles
- spacing scale
- typography definitions
- elevation tokens
- motion tokens
- icon metadata
- KitchenKin domain models
- accessibility guidance
- component contracts
- formatting utilities
- validation helpers
- shared TypeScript types

This package MUST NOT depend on:

- React DOM
- React Native
- Next.js
- shadcn
- Radix
- Base UI
- Framer Motion
- Reanimated

It should be pure TypeScript.

---

2. kkds-web

Contains the current web implementation.

Responsibilities:

- React components
- semantic HTML
- browser accessibility
- CSS
- current primitive foundation
- web-specific interactions
- browser motion
- RSC compatibility

This package consumes kkds-common.

---

3. kkds-mobile

This package does NOT exist yet.

Do not create it.

Instead, prepare the architecture so that it could exist later.

Examples:

- avoid leaking DOM concepts into shared contracts
- avoid browser-specific naming
- identify assumptions that would make mobile difficult
- identify APIs that should become platform-neutral

---

PHASE 1

Perform a complete architecture audit.

Identify:

- files that belong in kkds-common
- files that should remain web-only
- browser assumptions
- React assumptions
- DOM assumptions
- Next.js assumptions
- motion assumptions
- accessibility assumptions
- styling assumptions

Produce a migration plan before changing code.

---

PHASE 2

Extract platform-neutral pieces.

Examples include:

- tokens
- interfaces
- shared enums
- utility functions
- recipe metadata models
- allergen models
- formatting helpers
- semantic component contracts

Do NOT move React components into kkds-common.

---

PHASE 3

Review every exported component.

For each component classify it as:

Platform-neutral concept

or

Web implementation

Example:

RecipeCard

Concept:
- canonical recipe summary
- image hierarchy
- metadata hierarchy
- loading behavior
- accessibility expectations

Implementation:
- article element
- Link
- CSS grid
- browser hover
- browser focus
- Framer Motion

Document this distinction.

---

PHASE 4

Review component APIs.

Find props that unnecessarily expose browser concepts.

For example:

href

onClick

MouseEvent

DOM refs

Replace only where appropriate with platform-neutral abstractions.

Do NOT force every API to become universal.

The goal is to avoid accidental web coupling.

---

PHASE 5

Review motion.

Separate:

semantic motion

from

implementation.

For example:

motion.feedback.fast

motion.overlay.enter

motion.navigation.standard

rather than embedding Framer Motion-specific values throughout the codebase.

The web implementation may continue using Framer Motion.

---

PHASE 6

Review icons.

Create a platform-neutral icon strategy.

SVG should remain the source of truth.

Document how future React Native icons could be generated without changing component APIs.

---

PHASE 7

Review documentation.

Add a page describing the architecture.

Include:

Design Principles

Architecture

Package Responsibilities

Future Mobile Strategy

Shared vs Platform-Specific

Explain why:

- design language is shared
- implementation is platform-specific

---

PHASE 8

Provide recommendations.

Do NOT implement React Native.

Instead answer:

- What is already well separated?
- What would make Expo difficult?
- Which abstractions are strongest?
- Which APIs should evolve before 1.0?
- Which assumptions should remain web-only?
- Which should move into kkds-common?

---

IMPORTANT

Avoid premature abstraction.

Do not invent cross-platform APIs simply because React Native exists.

Prefer:

shared concepts

over

shared implementations.

The web experience should remain excellent.

Future mobile should be enabled, not forced.

Finally, produce an architecture diagram illustrating the relationship between:

kkds-common

kkds-web

future kkds-mobile

KitchenKin Web

future KitchenKin Expo

and explain how components, tokens, documentation, and governance flow between them.
