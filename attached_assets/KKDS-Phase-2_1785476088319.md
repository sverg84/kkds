# KKDS Phase 2 — Extract the Product Design System

The first phase successfully reconstructed KitchenKin's visual identity:

* design tokens
* typography
* spacing
* color roles
* branded documentation
* shadcn/Radix primitive components

However, KKDS is currently too similar to a themed shadcn component library.

The goal of this phase is **not** to add more primitive components.

The goal is to evolve KKDS into a true **product design system** by extracting KitchenKin's reusable semantic components and interaction patterns.

---

## Important Constraints

Do **not** rebuild the KitchenKin application.

Do **not** migrate pages into KKDS.

Do **not** generate CRUD functionality.

Do **not** recreate the product.

Do **not** create GraphQL, Prisma, Auth, Next.js routing, API routes, or server actions.

Do **not** simply wrap every existing KitchenKin component.

Instead, identify which concepts represent reusable product abstractions.

Think like a senior design engineer designing a public design system rather than copying an application.

---

# First: Analyze

Before writing any code, inspect the uploaded KitchenKin source.

Do not limit the analysis to `components/ui`.

Instead inspect:

* app/
* components/
* features/
* layouts
* recipe pages
* profile pages
* forms
* loading states
* empty states
* search
* navigation
* repeated JSX structures
* repeated interaction patterns
* repeated visual hierarchy

Your task is to identify recurring product concepts.

---

# Produce an Audit

Before implementing anything, generate a report listing:

For every proposed abstraction:

* Name
* Why it exists
* Which files or repeated usages it came from
* What design language it captures
* Suggested public API
* Whether it is:

  * exported KKDS component
  * documentation pattern
  * application-only implementation
* Whether it should remain Server Component compatible
* Whether it requires `"use client"`
* Which lower-level KKDS primitives compose it

Do **not** begin implementation until this audit is complete.

---

# Component Taxonomy

Organize KKDS into four layers.

## 1. Foundations

These already exist.

Maintain and improve them.

Examples:

* colors
* typography
* spacing
* radius
* elevation
* shadows
* motion
* semantic tokens
* accessibility conventions

---

## 2. Primitives

Continue building on top of shadcn/Radix.

Do not reinvent accessible primitives.

Examples:

* Button
* IconButton
* Input
* Textarea
* Dialog
* Popover
* Tabs
* Tooltip
* Badge
* Skeleton
* Avatar

These should remain generic.

---

## 3. KitchenKin Components

This is the most important layer.

Infer reusable KitchenKin concepts from the application.

Likely examples include:

* RecipeCard
* RecipeImage
* FavoriteButton
* CategoryBadge
* AllergenBadge
* RecipeMetadata
* RecipeTime
* RecipeAuthor
* RecipeSearch
* SearchResult
* IngredientRow
* IngredientEditor
* InstructionStep
* RecipeStats
* RecipeHeader
* EmptyRecipesState
* RecipeCardSkeleton

Do **not** blindly create every item above.

Only promote concepts that genuinely recur in the source.

These components should compose primitives rather than duplicate them.

---

## 4. Patterns

Some UI should not become exported components.

Instead, document them as recommended compositions.

Examples:

Recipe Discovery

Recipe Detail

Profile Tabs

Recipe Creation Form

Loading Patterns

Search Experience

Pagination

Responsive Layout

Empty States

Error States

Document these visually rather than exporting monolithic components.

---

# Philosophy

KKDS should describe KitchenKin's visual language.

Not merely its implementation.

The design system should communicate things like:

* how recipes are represented
* how metadata is prioritized
* how food imagery is displayed
* spacing rhythm
* interaction hierarchy
* motion language
* accessibility expectations
* empty state philosophy
* loading philosophy

The resulting documentation should teach another engineer—or an AI agent—how to build KitchenKin interfaces without reading the KitchenKin application.

---

# AI-Oriented Documentation

Every exported component should include documentation for both humans and AI.

For each component, include:

Purpose

When to use it

When not to use it

Composition guidance

Accessibility notes

Example usage

Variants

Do not focus only on props.

Explain intent.

---

# Implementation Rules

Prefer composition.

Avoid duplication.

Extract repeated patterns.

Keep components framework-agnostic where practical.

Do not couple KKDS to KitchenKin's GraphQL layer.

Do not couple KKDS to Prisma.

Do not couple KKDS to Auth.

Do not embed server actions.

Interactive components should own their `"use client"` boundaries.

Server-compatible components should remain usable from React Server Components.

---

# Deliverables

After the audit, implement:

* the semantic KitchenKin component layer
* documentation pages
* example compositions
* visual usage examples
* accessibility notes
* AI guidance
* component relationships

The finished KKDS should feel comparable to a professional product design system (such as Coinbase CDS, Shopify Polaris, or GitHub Primer), where the design language extends beyond primitive UI widgets into reusable product semantics.
