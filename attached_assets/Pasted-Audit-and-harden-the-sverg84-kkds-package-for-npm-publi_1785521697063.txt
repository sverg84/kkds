Audit and harden the `@sverg84/kkds` package for npm publication.

Do not publish the package yet.

The package currently builds with `tsup`, exports ESM, CJS, declarations, tokens, and styles, and includes a documentation app. I want you to verify the package architecture, apply only justified fixes, and prove that the packed tarball works in a clean consumer before publication.

Work in phases and report your findings before making broad changes.

PHASE 1 — INSPECT THE CURRENT PACKAGE

Inspect:

- `package.json`
- `src/index.ts`
- `src/index.css`
- `tsup.config.*`
- `tsconfig.json`
- all KKDS component files
- all exported shadcn/Radix primitive files
- generated files in `dist`
- `tokens.json`
- token build scripts
- the current npm tarball contents

Determine:

1. Why raw `.tsx` files appear in `dist/components`.
2. Whether any generated JavaScript or declaration files retain unresolved imports using:
   - `#components/*`
   - `#lib/*`
   - `#hooks/*`
3. Whether `dist/styles.css` is browser-ready compiled CSS or unprocessed Tailwind source.
4. Whether React and React DOM are externalized rather than bundled.
5. Whether `"use client"` directives survive for interactive components.
6. Whether non-interactive KKDS components remain usable from React Server Components.
7. Whether every package export points to a file that exists after a clean build.
8. Whether all runtime dependencies are necessary for the current public exports.
9. Whether the package currently exposes more shadcn primitives than KKDS intends to support publicly.

Before editing, summarize the findings and the exact changes you recommend.

PHASE 2 — CLEAN THE BUILD OUTPUT

The current `build:lib` script contains a source-copying step similar to:

`cp -r src/components dist/components`

If those raw `.tsx` files are not required by a supported package export, remove that copy step.

Update the library build so it:

1. Deletes `dist` before building.
2. Generates tokens.
3. Builds JavaScript and declaration output with `tsup`.
4. Produces the distributable stylesheet.
5. Does not leave stale files from previous builds.
6. Does not publish raw source files unless there is a deliberate, documented reason.

Do not remove source files from the repository. Only stop copying unnecessary source files into the published `dist`.

PHASE 3 — VERIFY PACKAGE ALIASES

Inspect the package-level `imports` field:

- `#components/*`
- `#lib/*`
- `#hooks/*`

Because `src` is not included in the published package, ensure no published JavaScript or declaration file depends on aliases that resolve to missing `src` files.

Run an equivalent of:

`grep -R '#components\|#lib\|#hooks' dist`

If no generated output uses these aliases, remove the `imports` field from the published package manifest unless it is still needed for local tooling.

If generated output retains these aliases, fix the build so they are resolved or rewritten. Do not publish aliases that point to absent source files.

PHASE 4 — HARDEN PACKAGE METADATA

Review and update `package.json` where appropriate.

The package should have valid entries for:

- `main`
- `module`
- `types`
- `exports`
- `files`
- `sideEffects`
- `peerDependencies`
- `publishConfig`

The intended public entry points are:

- `@sverg84/kkds`
- `@sverg84/kkds/tokens`
- `@sverg84/kkds/tokens.json`
- `@sverg84/kkds/styles.css`
- optionally `@sverg84/kkds/package.json`

Ensure the `exports` map points to real generated files.

Add:

unless inspection shows a more accurate stylesheet side-effect configuration is required.

Use bounded React peer ranges rather than an unbounded future-major range:

- `react`: `^18.2.0 || ^19.0.0`

Add:

`"publishConfig": {
  "access": "public",
  "registry": "https://registry.npmjs.org/"
}`

Do not move React or React DOM into runtime dependencies.

PHASE 5 — VERIFY THE STYLESHEET

Inspect `src/index.css`.

If it contains Tailwind build-time directives such as:

- `@import "tailwindcss"`
- `@theme`
- `@source`
- other directives that require a consumer-side Tailwind build

do not merely copy it and call it compiled CSS.

Choose and implement one clear distribution strategy:

Preferred strategy:
- Build a browser-ready `dist/styles.css`.
- Consumers should be able to import:
  `import "@sverg84/kkds/styles.css";`
- The consumer should not need to process KKDS source through Tailwind merely to receive the package styles.

If producing fully compiled CSS is not feasible because classes must be generated by the consuming application, document that limitation explicitly in the README and configure the package consistently. Do not present unprocessed source CSS as standalone compiled CSS.

Verify the final stylesheet contains the KKDS tokens and component styles needed by a separate application.
